# MOMO-Redesign 🎬

### 영화를 메모하다 — 영화 기록 서비스 UI 리디자인

MOMO-Redesign은 기존 팀 미니 프로젝트 **MOMO**를 기반으로, 프론트엔드의 디자인 일관성과 사용자 경험을 개선하기 위해 진행한 개인 리디자인 프로젝트입니다.

영화 검색과 상세 정보 조회, 리뷰 작성, 관심 영화 관리, 회원 기능 등 기존 서비스의 핵심 기능을 유지하면서 전체 화면에 새로운 디자인 시스템을 적용했습니다.

기존 프로젝트의 기능을 무조건 새로 만드는 것이 아니라, **기존 서비스의 구조와 동작을 보존하면서 화면의 완성도와 일관성을 높이는 것**을 목표로 했습니다.

## 2. 리디자인 배경

기존 MOMO는 영화 검색, 리뷰, 회원 관리 등 주요 기능을 갖추고 있었지만 화면 간 시각적 일관성에 개선 여지가 있었습니다.

특히 어두운 헤더와 밝은 본문 영역의 대비가 크고, 페이지마다 사용되는 배경색과 카드·입력 요소의 표현이 달라 전체 서비스가 하나의 디자인으로 연결되지 않는 문제가 있었습니다.

이를 개선하기 위해 다음 방향으로 작업했습니다.

- 서비스 전체에 공통 디자인 기준 적용
- 헤더와 본문 사이의 시각적 불일치 개선
- 카드, 버튼, 검색창, 입력창의 색상 및 상태 표현 통일
- 텍스트와 배경 간 대비 및 가독성 보완
- 기존 페이지 구조와 주요 기능 보존

## 3. Cinema Charcoal 디자인 시스템

영화 아카이브 서비스에 어울리는 차분한 분위기를 목표로 **Cinema Charcoal** 디자인을 선정했습니다.

짙은 차콜 계열을 중심으로 화면을 구성하고, 주요 액션에는 테라코타 계열의 포인트 색상을 사용했습니다.

### 컬러 팔레트

| 구분             | HEX       | 적용 영역          |
| -------------- | --------- | -------------- |
| Header         | `#222222` | 헤더 및 주요 상단 영역  |
| Background     | `#303030` | 페이지 기본 배경      |
| Card           | `#424242` | 카드 및 콘텐츠 컨테이너  |
| Primary Text   | `#F0ECE6` | 제목과 주요 본문      |
| Accent         | `#C0785A` | 주요 버튼 및 강조 요소  |
| Border         | `#5A5552` | 카드 경계선 및 구분선   |
| Secondary Text | `#BEB8B2` | 부가 정보 및 보조 텍스트 |

### 디자인 적용 원칙

**일관성**

페이지마다 다른 스타일을 적용하기보다 공통 색상 토큰을 사용해 전체 서비스의 시각적 통일성을 확보했습니다.

**가독성**

짙은 배경에서도 주요 정보와 보조 정보가 구분되도록 텍스트 대비, 카드 경계선, 입력 상태를 조정했습니다.

**강조 요소의 절제**

모든 버튼과 링크를 포인트 색상으로 처리하지 않고, 주요 액션에만 Accent를 사용했습니다. 보조 액션은 중립색을 적용해 시각적 우선순위를 구분했습니다.

**기존 기능 보존**

리디자인 과정에서 기존 화면의 라우팅, API 연동 방식, 인증 및 비즈니스 로직은 유지했습니다.

## 4. 프론트엔드 개선 과정

### Phase 1 — 기존 서비스 점검 및 기능 안정화

리디자인 작업에 앞서 기존 서비스의 동작과 API 연동을 점검하고, 일부 화면 기능을 보완했습니다.

주요 개선 사항은 다음과 같습니다.

- 영화별 리뷰 조회 화면 및 API 연동 점검
- 댓글 추가 조회 기능 보완
- 회원가입 아이디 입력 길이 검증
- 프로필의 리뷰 개수 집계 보완
- 기존 화면과 변경 기능의 회귀 테스트

### Phase 2 — 홈 화면 디자인 적용

전체 페이지를 동시에 수정하기 전에 홈 화면에 Cinema Charcoal을 시범 적용했습니다.

기존 홈 화면 구성은 유지하면서 헤더, 본문 배경, 카드, 텍스트 및 검색 요소의 색상을 변경했습니다.

이후 실제 적용 화면을 검토하여 보조 텍스트, 경계선, 검색창 및 버튼의 대비를 추가 보정하고 디자인 기준을 확정했습니다.

### Phase 3 — 전체 페이지 디자인 통일

홈 화면에서 확정한 디자인 기준을 나머지 페이지와 공통 컴포넌트에 확대 적용했습니다.

**적용 화면**

- 홈 및 영화 검색
- 영화 상세 및 배우·감독 상세
- 전체 리뷰 및 영화별 리뷰
- 리뷰 상세·작성·수정
- 로그인 및 회원가입
- 마이페이지 및 프로필 수정
- 내가 작성한 리뷰 및 좋아요한 리뷰
- 관심 영화 및 회원탈퇴

**공통 UI 요소**

- 헤더 및 푸터
- 검색창 및 자동완성
- 카드와 버튼
- 입력창 및 입력 검증 안내
- 오류 안내 및 토스트 알림
- 채팅 및 이미지 확대 모달

공통 색상 관리를 위해 다음 스타일 파일을 추가했습니다.

```text
momo-frontend/src/styles/redesign/
├── CinemaCharcoal.tokens.js
├── CinemaCharcoal.styles.js
├── HomeTheme.styles.js
└── ...
```

색상 역할을 토큰으로 분리하고, 공통 스타일과 페이지별 스타일에 적용했습니다.

## 8. 로컬 실행 방법

### 준비 환경

- Java 21
- MySQL 8
- Node.js 및 Yarn
- 기존 MOMO 데이터베이스 및 외부 API 설정
- JWT 및 Firebase 인증 설정

### 백엔드 실행

저장소 루트 기준 Windows PowerShell:

```powershell
.\momo-backend\gradlew.bat -p .\momo-backend bootJar

java -jar .\momo-backend\build\libs\momo-backend-0.0.1-SNAPSHOT.jar --spring.jpa.hibernate.ddl-auto=validate
```

기존 데이터베이스 스키마와 실행 설정을 먼저 확인해야 합니다. 초기화 또는 스키마 자동 변경을 전제로 실행하지 않습니다.

### 프론트엔드 실행

```powershell
cd momo-frontend
yarn install --frozen-lockfile
yarn start
```

기본 개발 환경은 다음과 같습니다.

- React: `http://localhost:3000`
- Spring Boot: `http://localhost:8111`

실행 환경에 따라 API 주소, CORS, WebSocket 및 Firebase 설정이 추가로 필요할 수 있습니다.

## 11. 제3자 로그인 및 소셜 회원 기능 개선 — 2026.11.20

UI 리디자인 이후 **Kakao / Naver / Google 소셜 로그인**을 추가하고, 기존 LOCAL 계정과 함께 사용할 수 있도록 인증 구조와 회원 기능을 개선했습니다.

### 지원 기능

| 기능 | 개선 내용 |
|---|---|
| 소셜 로그인·자동 가입 | 공급자 인증 후 처음 방문한 회원은 자동 등록하고, 재로그인 시 기존 MOMO 회원으로 연결 |
| JWT 세션 | 일반·소셜 인증 성공 후 공통 흐름에서 MOMO Access Token·Refresh Token 발급 |
| 소셜 프로필 | 이메일이 없어도 닉네임 수정 가능, 공급자 이메일은 읽기 전용·없으면 미등록 표시 |
| 회원 유형별 처리 | LOCAL은 기존 비밀번호 인증 유지, 소셜 회원에게는 MOMO 비밀번호 변경·확인을 요구하지 않음 |
| 탈퇴 안내 | 동의·확인 문구 검증 유지, 네이버·Google은 추가 계정 확인과 자동 후속 탈퇴를 사전에 안내 |

### 공통 OAuth 구조와 계정 식별

- `OAuthController`·`OAuthStateService`로 세 공급자의 진입과 상태 관리를 통합하고, 공급자별 코드 교환·신원 검증은 유지했습니다.
- `SocialLoginService`는 회원 조회·자동 가입, `LoginSessionService`는 일반·소셜 공통 JWT 발급·Refresh Token 저장을 담당합니다.
- 회원은 **`provider + providerId`**로 식별합니다. 이메일이 같다는 이유로 LOCAL 계정이나 다른 공급자 계정을 자동 연결하지 않습니다.
- Google의 PKCE(S256)·nonce·ID Token 검증을 유지하고, 서버에서 LOGIN/DELETE 목적·공급자·탈퇴 대상 회원을 구분합니다.
- 로그인과 탈퇴는 공통 React Flow·Callback을 사용하되 완료 처리를 분리합니다. 중복 코드 교환과 계정 전환 후 도착하는 이전 응답을 차단합니다.

### 회원 탈퇴 및 자동 연결 해제

| 회원 유형 | 처리 흐름 |
|---|---|
| LOCAL | 기존 MOMO 비밀번호 확인 → 회원 정보 삭제 |
| KAKAO | 서버 Admin Key와 저장된 공급자 ID로 Unlink → 성공 후 회원 정보 삭제 |
| NAVER·GOOGLE | OAuth 계정 확인 → 현재 MOMO에 연결된 동일 계정인지 비교 → 새 Access Token으로 Revoke → 성공 후 회원 정보 삭제 |

외부 연결 해제 후 MOMO 회원·관련 데이터·Refresh Token을 정리합니다. **네이버·Google 계정 자체를 삭제하는 기능은 아닙니다.** 공급자 토큰은 필요한 서버 처리 동안만 사용하고 DB에 장기 저장하거나 브라우저에 전달하지 않습니다.

외부 해제 실패·결과 불명 시 내부 삭제를 중단합니다. 해제 성공 후에는 롤백이 확인된 일시적 DB 잠금 오류에 한해 삭제만 제한적으로 재시도합니다. 외부 해제와 DB 삭제는 원자적이지 않으며 서버 재시작 후 부분 실패의 자동 복구는 보장하지 않습니다.

### 검증 및 개발환경

- **자동화 검증:** 일반 인증 회귀, 소셜 가입·재로그인, JWT·Refresh Token Rotation, state·Google 검증, 프로필·탈퇴·실패 처리 등을 H2·모의 HTTP·React 테스트로 확인했습니다.
- **개인 환경 실사용 검증:** 세 공급자의 로그인·자동 가입·프로필 수정·탈퇴·자동 연결 해제·MySQL 회원 삭제·동일 계정 재가입을 직접 확인했습니다. 모의 응답 기반 자동화 결과와 구분합니다.
- **설정:** 공급자별 `CLIENT_ID`·`CLIENT_SECRET`·`REDIRECT_URI`와 서버 전용 `KAKAO_ADMIN_KEY`를 준비합니다. 실제 비밀값·인증 JSON·토큰은 Git에 추가하지 않습니다.
- **DB 적용:** 기존 컬럼·제약과 데이터 백업을 먼저 확인하고, 이미 적용된 스키마 SQL은 재실행하지 않습니다.

세부 클래스 역할·API·실패 처리와 설정 방법은 [OAuth 구조 개선 안내](momo-backend/docs/OAUTH_IMPROVEMENT.md)를 참고하세요.


## RAG 6차시 — Atlas·OpenAI 및 AI 도우미

기존 StubEngine과 5차시 색인 상태·권한·원본 보호 구조를 유지하면서 `RAG_ENGINE=atlas`를 선택할 수 있습니다. Atlas 모드는 MongoDB Vector Search와 OpenAI 임베딩·답변 생성을 사용합니다. Stub 모드는 외부 연결 없이 개발·자동 테스트에 사용하며 장애 시 자동 대체하지 않습니다.

- 일반 리뷰 등록·수정 후 색인은 전용 작업자 2개·대기열 50개로 제한해 비동기 처리합니다. 미완료 INDEXING은 기존 운영자 재색인으로 복구합니다.
- 질문은 READY 원본에 한정하고, 검색 전후 fingerprint를 확인합니다. 근거·인용 검증 실패 시 답변 전체를 보류합니다.
- 로그인 후 AI 도우미에서 ALL/MINE 질문, 답변·출처·실행 경로를 확인합니다. 질문과 검색 근거 리뷰가 외부 AI 서비스로 전달됨을 안내합니다.
- 호출 제한은 메모리 기반 안전장치이며 재시작·다중 인스턴스의 금전적 절대 예산 상한은 아닙니다.

설정 이름·엔진 전환·초기 재색인·사용자 직접 검증 절차는 [RAG 문서의 6차시 안내](docs/RAG.md#6차시-atlasopenai-전환과-사용자-검증)를 따릅니다. 실제 유료 OpenAI 호출과 운영 Atlas 검증 결과는 자동 Mock 테스트와 구분합니다. 기존 UI·OAuth 설명은 보존합니다.


6차시 실제 연동은 사용자가 개인 환경에서 Atlas 벡터 검색·실제 OpenAI 임베딩/GPT-4.1-mini 답변·ALL/MINE 접근 범위·10건 재색인·React·리뷰 작성/수정/삭제 반영을 확인했습니다. 자동 Mock 결과와 구분하며 실제 MySQL 동시성 8건 SKIP 등 잔여 한계는 유지합니다. 설정 오류 해결과 시연 데이터 사용법은 [RAG 기술 문서](docs/RAG.md)를 참고하세요.
